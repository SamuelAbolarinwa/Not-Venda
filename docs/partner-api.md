# Partner API contract

Samuel owns the web/database/authoritative retail engine. The partner owns WhatsApp transport, speech and model orchestration. Groq is the initial model experiment; official N-ATLAS speech is a separate dependency. No model gets database credentials or unrestricted database tools.

`openapi.json` contains only implemented foundation paths. `openapi-planned.json` is a non-executable draft contract for Packet 2/4; no handler returns pretend sales or receipts.

## Implemented now

Bearer Supabase user access token required for `/v1`. Server independently verifies the token and current active shop membership. `GET /v1/me`, `GET /v1/shops`, `POST /v1/shops`, `GET /v1/shops/{shopId}/catalogue`, `POST /v1/shops/{shopId}/products`, and `GET /v1/shops/{shopId}/products/{productId}`. The product POST is owner-only and creates aliases, units and initial price together. Lists accept limit 1–100 (default 30), offset 0–100000; stable creation/id ordering. Missing or inaccessible shop uniformly returns 403 to prevent tenant discovery. Unknown routes and missing products within an authorised shop return 404.

All prices are canonical decimal strings in kobo (`"150000"` = ₦1,500). Never use JSON numbers for money. Product prices are per base unit; multipliers are positive integers. Responses contain server request UUID in `x-request-id`. Error body: `{"code":"FORBIDDEN","message":"You do not have permission for this shop","request_id":"…"}`. Safe optional details may be added. Codes include UNAUTHENTICATED (401), FORBIDDEN (403), INVALID_INPUT (400), CONFLICT (409), PAYLOAD_TOO_LARGE (413), DATABASE_UNAVAILABLE/AUTH_UNAVAILABLE (503), INTERNAL_ERROR (500), NOT_FOUND (404).

Shop creation body (contract example):

```json
{
  "request_id": "490296aa-0b58-4f75-b7a8-a1b892c0dc95",
  "name": "Ade’s Corner Shop"
}
```

Persist that UUID until a response is known. Replay with the same actor/name returns the same shop, including after a lost response; changing the name returns 409. Request IDs for tracing are independently generated by the server. Product creation is transactional but **not replay-safe** in Packet 1: inspect catalogue after an uncertain response; do not automatically retry its POST.

## Planned only — assistant and WhatsApp

Transport authentication is a scoped partner credential plus server-verified, owner-approved WhatsApp link. A model-supplied user ID, phone number or shop ID is never authority. Actor context returns permitted shops/capabilities for the verified link. Expired/revoked links stop access immediately. Partner credential issuance, signature validation and linking routes will be implemented in Packet 4; no partner keys are currently accepted.

The proposed operation protocol uses an `Idempotency-Key` UUID, scoped to actor/shop/operation. The partner persists it across duplicate webhook deliveries and retries. Same key + same canonical payload returns the original operation; changed payload returns IDEMPOTENCY_CONFLICT (409). Concurrent duplicate commits serialise to one ledger transaction. A timeout is unknown, not failure: query operation lookup with the key before retrying. Retention and canonicalisation rules must be finalised before Packet 2 implementation.

1. Resolve `/v1/assistant/context` and look up the authenticated shop catalogue. Capture channel/verified link as metadata, never permissions from the model.
2. Create `/v1/shops/{shopId}/drafts` from interpreted intent with a stable key; return draft UUID, version and warnings. Correction PATCH supplies expected_version; conflicts return 409.
3. Preview `.../drafts/{draftId}/preview` returns server-calculated lines, price/unit versions, totals, payment breakdown and expiry. No stock/money is committed.
4. User explicitly confirms the exact preview/version through `.../confirmations`. Server issues short-lived, one-use opaque confirmation token bound to actor, shop, draft, version and preview hash. No transcript ambiguity or assistant inference counts as confirmation.
5. Commit `.../drafts/{draftId}/commit` with expected_version, confirmation token and stable key. Revalidate permission, versions, availability and payment rules in one transaction. Commit creates operation, authoritative ledger entries and receipt, or nothing.
6. Lookup `.../operations/by-key/{idempotencyKey}` recovers committed, pending or rejected state after uncertain response. `/receipts/{receiptId}` returns only committed authoritative receipts.
7. WhatsApp link request is pending until owner approval in authenticated app; approve/revoke with audit. Revocation invalidates actor context and outstanding confirmations. Identity proof, number reassignment and recovery require Packet 4 review.

Planned errors additionally include STALE_DRAFT, STALE_PRICE, CONFIRMATION_EXPIRED, CONFIRMATION_REQUIRED, IDEMPOTENCY_CONFLICT, LINK_REVOKED and OPERATION_PENDING. Invalid input is 400; unauthenticated 401; permission/link failures 403; missing authorised resources 404; stale/conflict 409; expired confirmation 410; rate limits 429; temporary dependency failure 503. Retry 429/503 with bounded backoff/jitter and Retry-After when present; never blindly retry a financial action with a new key. Re-preview and obtain fresh explicit confirmation after any relevant change. Planned receipts include receipt_id, operation_id, shop_id, committed_at, immutable line/payment snapshots and exact decimal-string totals.
